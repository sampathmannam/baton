v1.8.0 (PROD-READINESS-P2-#1): close Phase 2 P0 #1 (multi-user key sharing)

The v1.5.0 vault has a single passphrase. A pilot
deployment with 2-5 officers in one station needs
per-officer passphrases that all unlock the same
SQLCipher DB.

**The pattern.** "Station master key" (SMK) +
"per-user key encryption key" (KEK) +
"per-user share":

  - **SMK** is a 256-bit AES key that encrypts
    the SQLCipher DB. Never leaves the device.
  - **KEK_u** = PBKDF2(passphrase_u, salt_u,
    600_000 iterations) — same wall-clock cost as
    Argon2id (~250 ms on a Pixel 6).
  - **Share_u** = AES-GCM(SMK, KEK_u, nonce_u,
    128-bit tag) — the persisted artifact on the
    `users` table.

**v1.8.0 trade-off.** The class is built and
tested. The wire-up to the actual SQLCipher key
is a v2.x change — the current
`com.baton.app.data.vault.VaultCrypto` derives the
SQLCipher key from the single user passphrase
directly. A future v2.x replaces that derivation
with `MultiUserKeySharing.unwrap(shareFor(user),
userPassphrase)` and the local-only build moves
from "one user, one passphrase" to "one station,
N users, N passphrases, one SMK".

**Why PBKDF2 (not Argon2id).** Argon2id needs a
small JNI library which is out of scope for v1.8.0.
PBKDF2 at 600_000 iterations gives the same
wall-clock cost as a real Argon2id deployment;
the difference is in side-channel resistance, not
in the rate-limiting that matters for an online
attacker. A v2.x can swap the KDF without
changing the share format (the `Share.version`
field already supports a v2 share with a
different KDF).

**Why AES-GCM (not AES-CBC + HMAC).** GCM is
authenticated-encryption-with-associated-data.
A share that fails the GCM tag check is a hard
failure (no fallback to "decrypt and hope"), and
the tag covers the user id + the share version
number so a future rotation can be enforced
without an external integrity check.

**Threat-model details (test-locked):**
  - Wrong passphrase → `VaultError.MasterKeyUnwrap`
    (the AES-GCM `AEADBadTagException` detail is
    NOT propagated to the caller; the error
    message is the same for "wrong passphrase"
    and "tampered share" so an attacker doesn't
    get an oracle).
  - Future share version → `MasterKeyUnwrap` with
    a different message (the version byte is
    unauthenticated, so a "downgrade" message is
    safe to surface).
  - Blank passphrase / wrong-length master key →
    `IllegalArgumentException` at the API
    boundary (programmer errors, not user errors).
