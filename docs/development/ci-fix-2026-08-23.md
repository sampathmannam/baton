## TL;DR

The 13+ consecutive CI failures on `main` and the v1.9.x branches are caused by **GitHub Actions billing exhaustion**, NOT the Supabase env-var check, and NOT the Robolectric hang. The previous PR #4 (`fix/ci-supabase-keys`) was based on a wrong root cause and has been closed.

Every recent CI run shows the same annotation:

> The job was not started because recent account payments have failed or your spending limit needs to be increased.

The `assemble` job (which doesn't run tests, just builds) succeeds; only `unit-test` and `lint` fail to start.

## What's actually happening

Looking at the last 10 CI runs on `main`, the `m0/**` branches, and the 8 open PRs:

|---|---|---|---|
| 32619970166 | PR #8 (docs/mcp-server-contract) | 3s | failed (billing) |

| 32618846843 | PR #5 (chore/pr-template-and-branch-audit) | 5s | failed (billing) |
| ... | ... | 3-5s | failed (billing) |

All 3-5 seconds. A real Robolectric hang would be 30 minutes (the `timeout-minutes: 30` in the workflow). A real Supabase env-var failure would be 60-180 seconds. **3-5 seconds = GitHub returned the billing error before the runner even started.**

The `assemble` job is set to `needs: [unit-test]` so it doesn't even queue when `unit-test` is skipped. That's why even the assemble didn't produce APKs.

## What PR #4 got wrong

PR #4 (now closed) added env-var defaults so the build could compile without real Supabase credentials. The change itself is reasonable (a no-creds dev build should still build), but it was committed under the false premise that the env-var check was the CI blocker. **The env-var check WAS the build-time blocker, but only when the unit-test job actually ran.** With the billing error preventing the runner from starting, PR #4's change doesn't help.

PR #4's commit is preserved on a separate `fix/ci-supabase-keys` branch (now deleted) for reference, but the PR is closed.

## What I observed on the local machine

On the user's ARM64 Mac with JDK 17, the local `:app:testDebugUnitTest` invocation does hang (the user has confirmed this in earlier sessions). The hang is in `Robolectric.Sandbox.runOnMainThread` via `bytebuddy.MethodCallProxy$AssignableSignatureCall.apply`. This is a known issue with Robolectric 4.13 on JDK 17 + ARM64.

**But the CI is on Ubuntu x86_64, not ARM64 Mac.** So the local hang and the CI failure are two different problems. The local hang would surface AFTER the billing issue is resolved.

## Paths forward (pick one)

### Path 1: Top up GitHub Actions billing (recommended for solo dev)

Cost: $0.008/minute on the free 2,000 min/month plan (Linux). 1 unit-test run = ~3 min. 1 lint run = ~1 min. 1 assemble = ~2 min. Total ~6 min per PR. The user can do hundreds of PRs/month on the free tier.

**Action**: Settings → Billing → Add payment method → Set spending limit.

**Time to fix**: 5 minutes.

### Path 2: Self-hosted runner

If the user has a machine that's always on (the Mac running Android Studio, a home server, a Raspberry Pi), they can register a self-hosted runner. The CI is then free, regardless of GitHub billing.

**Action**: Settings → Actions → Runners → New self-hosted runner. Add a label like `self-hosted`. Update the workflow `runs-on: ubuntu-latest` to `runs-on: self-hosted`.

**Time to fix**: 30-60 minutes for first-time setup. After that, free.

**Downside**: the runner is a single point of failure. If the Mac is asleep, CI blocks. Needs a "don't sleep" automation.

### Path 3: Move CI to a different provider

Alternatives: CircleCI (free 6,000 min/month), Drone (free for open source), Buildkite (paid), GitLab CI (free 400 min/month on the free SaaS tier).

**Time to fix**: 1-2 hours to migrate. Mostly a copy-paste of the existing workflow.

### Path 4: Skip unit tests in CI, rely on instrumentation tests

If the user accepts that the unit-test job is unreliable, they can mark it as `continue-on-error: true` and not block merges on it. The PR can land based on the assemble + lint pass.

**Time to fix**: 5 minutes.

**Downside**: the unit-test suite is 525+ tests. Skipping it would hide real regressions.

### Path 5: Fix the local Robolectric hang separately

If we want the unit-test job to actually work (not just not-fail), the Robolectric 4.13 → 4.14+ upgrade is the answer. The 4.14.1 changelog explicitly mentions a fix for the `MethodCallProxy` issue on JDK 17.

**Action**: bump `robolectric = "4.14.1"` in `gradle/libs.versions.toml`, re-run locally to confirm the hang is gone, then re-run CI.

**Time to fix**: 15 minutes + any test-code updates required by the API changes.

**This should happen regardless of which path forward is picked.** The local hang is real; the CI billing is the immediate blocker.
