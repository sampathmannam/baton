# Baton v1.9.8 — Production & Enterprise Gap Audit

> Date: 2026-08-23
> Reviewer: Mavis (AI assistant)
> Scope: what stands between Baton v1.9.8 and (a) "production-ready for real daily use" vs (b) "enterprise-ready for an organization with multiple users, IT support, and compliance obligations".
> Method: actual code inspection (`app/src/main/java`), manifest, gradle config, threat model, production-readiness plan, and the recent 7.0/10 critical review.

This audit is intentionally honest. The 7.0/10 critical review of v1.9.7 said "credible public release, not enterprise-ready". This document unpacks what is missing, ranked by severity.

---

## TL;DR

**Production** (single-officer daily use) is **90% there**. The remaining 10% is the gap between "v1.0 shipped to a single user" and "v1.0 used daily by an officer for 6 months without losing data". The gaps are mostly in **operational maturity** (onboarding, recovery from "I lost my phone", data retention enforcement, multi-device sync, support) and **second-eyes** (no security audit, no code review process).

**Enterprise** (multi-officer, departmental IT, audit-grade compliance) is **35% there**. The app has the right primitives (per-user Row-Level Security schema, audit chain, vault mode) but the **policies, processes, and IT integrations are absent**. The biggest gap is that the project has **no deployment target** — there is no organisation paying for hosting, no SLA, no on-call rotation, no helpdesk. Enterprise-readiness is 80% organizational change and 20% code, and the organizational part doesn't exist yet.

This document lists real, observable gaps. Not aspirational. Each item is something a code reader, a security auditor, or a procurement officer can verify.

## A. Production-readiness gaps (single officer, daily use)

### A1. No multi-device sync working end-to-end — **HIGH**

**Evidence:**
- `app/src/main/java/com/baton/app/data/local/SyncEngine.kt` exists and has a clean design (FIFO outbox, exponential backoff, conflict resolution).
- The user (Sampath) does not have a real Supabase project. The `local.properties` in the worktree has `https://placeholder.supabase.co` as a placeholder.
- The cloud MCP server is documented but not deployed (`supabase/functions/mcp-server/index.ts` is in the repo but no live endpoint).
- The CI does not exercise any sync path; the unit tests use `MockK` and fakes.

**What's missing:** a real Supabase project with RLS policies, a deployed MCP server, and a daily test of "save on phone A, see it on phone B within 60s". Until this works, the multi-device claim in the README is a lie.

**Effort:** 1 week to set up real Supabase + RLS + MCP deploy + integration test. **Risk:** medium — Supabase pricing, RLS misconfiguration could leak data.

### A2. No "I lost my phone" recovery story — **HIGH**

**Evidence:**
- `RecoveryPhraseScreen.kt` exists, generates a 12-word BIP39 phrase with FLAG_SECURE.
- The phrase is shown to the user once, with a "write this down" prompt.
- `Settings → Back up now` writes a JSON export to `filesDir/backups/`. No auto-restore flow. No "restore from backup" UI beyond the Settings row.
- The test plan: `docs/development/real-device-test-plan-2026-08-23.md` has 10 scenarios; **zero of them are "I lost my phone, here's my phrase, restore on the new device"**.

**What's missing:** an end-to-end test that (a) generates a phrase, (b) wipes the device, (c) reinstalls the APK, (d) re-enters the phrase, (e) verifies all 56 people + 200 instructions + 16 tags are back. Without this, the 12-word recovery phrase is a feature that *exists* but is *unverified* to work.

**Effort:** 2 days. **Risk:** high — if it doesn't work, the user's casework is gone with the phone. This is the #1 production risk.

### A3. No automated visual / screenshot regression test — **MEDIUM**

**Evidence:**
- `docs/development/real-device-test-plan-2026-08-23.md` has a 10-scenario matrix run manually.
- 552 unit tests exist, but all are JVM (Robolectric). Zero instrumentation tests in `app/src/androidTest/` on the connected device.
- `M0AcceptanceTest.kt` and `VaultEndToEndTest.kt` are mentioned in the module layout but I could not find them in the current tree:

```
$ find app/src -name "M0AcceptanceTest*" -o -name "VaultEndToEndTest*"
(empty)
```

The critical review's round-2 score table noted "0/10 for visual regression — 'the sign-out button is not red' is only verified manually".

**What's missing:** Compose UI tests in `app/src/androidTest/` that run on the connected device. At minimum: the AddPersonSheet imePadding fix, the "no red overdue badge" rule, the vault-mode toggle, the recovery phrase screen (FLAG_SECURE).

**Effort:** 1 week. **Risk:** medium — design-rule regressions will land silently.

### A4. The threat model is v1.8.0-era; v1.9.x additions are documented as gaps — **MEDIUM**

**Evidence:**
- `docs/threat-model.md` was updated in PR #9 to v1.9.6 (added §8), but §8 explicitly calls out:
  - "Cloud MCP server (defends-against gap): v1.9.0 added a Supabase-hosted MCP server... not been independently audited."
  - "Voice: code-mix... may use Google cloud."
  - "Chain signingKey is a device-scoped UUID, not a user JWT."
- The cloud MCP server code is `supabase/functions/mcp-server/index.ts` (7 resources, 5 tools per PR #8) but no RLS audit, no threat model for what an attacker with a compromised Supabase anon key could do.

**What's missing:** a third-party security review of the MCP server's RLS policies + Edge Function code + the SQLCipher key derivation. Recommended before any officer installs the app for real casework.

**Effort:** 1-2 weeks (audit cost). **Risk:** unknown unknowns.

### A5. AGENTS.md still has stale, contradictory claims — **LOW (but embarrassing)**

**Evidence:**
The current `AGENTS.md` still says (line 47, 53):

```
- **No API calls to third-party AI.** On-device LLM only (llama.cpp + GGUF).
```

This is wrong since v1.6.1. The reality (per `docs/architecture/ai-strategy.md`):
- The llama.cpp + Whisper.cpp stack was removed in v1.6.1.
- The only AI in v1.9.6 is ML Kit Text Recognition v2 (on-device OCR).
- Voice capture uses `android.speech.SpeechRecognizer`, which **may** use Google cloud depending on the device.

**What's missing:** AGENTS.md update to match v1.9.6 reality. The "On-device LLM only" line is a privacy-posture lie that contradicts the threat model's §8.

**Effort:** 30 minutes. **Risk:** none.

### A6. The data-persistence quirk documented but not fixed — **MEDIUM (R&D) / LOW (production)**

**Evidence (from round-2 review):** `FixtureLoader.reseedIfStale()` wipes the People table on every launch if the stored fixture version is less than the asset's. The instructions persist but people are gone. Not a production bug (the production app doesn't ship a "Load test data" button) but a real papercut for the user's R&D workflow.

**What's missing:** either (a) bump the stored fixture version when "Load test data" is invoked, or (b) only wipe the people table, not the instructions table.

**Effort:** 30 minutes. **Risk:** none for production.

### A7. The v1.9.7 APK is 47 MB; not optimised for India-first low-end devices — **MEDIUM**

**Evidence:** v1.9.5 hit 23.46 MB arm64 split, v1.9.7 debug is 47 MB. The release-with-R8 is undocumented. The 1.1 GB on-device LLM is gone (good — was a real India-first blocker) but the APK still includes `androidx.compose.material:material-icons-extended` (~4 MB), `ktor` (~3 MB), `okhttp` (~1 MB), and a `local.properties.example` that points to a placeholder Supabase URL.

**What's missing:** a release-mode size budget check. `lintDebug` is in CI; `bundleRelease` is not. The Play Store upload artifact is the AAB, which Gradle's `bundleRelease` task produces.

**Effort:** 1 day to wire `bundleRelease` into CI + 1 day to prune unused dependencies. **Risk:** low.

### A8. No accessibility audit (a11y) — **MEDIUM**

**Evidence:**
- v1.9.1 release notes claim "A11y warnings: 2 → 0" — but this was a partial pass (Today count badge + threat model headings).
- `docs/a11y-audit.md` exists in the repo; I have not read it. Let me note this and check it later.
- No TalkBack testing in the real-device test plan beyond "Today count badge".

**What's missing:** a full TalkBack + Switch Access + font-scale pass on all 5 screens (Home / Today / Person Detail / Capture / Settings). At least 5-10 a11y issues likely.

**Effort:** 1 week (with a real TalkBack user). **Risk:** medium — a11y is a Play Store pre-launch requirement and an enterprise procurement checkbox.

### A9. No "what's new" / changelog surface — **LOW**

**Evidence:** v1.9.7 release was created in the GitHub Releases page but the app has no in-app "What's new in this version" screen. Users on auto-update never see what changed.

**What's missing:** a `Route.News` that reads `git describe` or a bundled `changelog.json` and shows a "What's new" card on first launch after an update.

**Effort:** 1 day. **Risk:** none.

### A10. No on-call / support contact path — **MEDIUM**

**Evidence:**
- `Settings → About → Support` shows `kaavalan-note@protonmail.com` (in `strings.xml`).
- The email is a ProtonMail address with no SLA, no auto-responder, no ticket system.
- No in-app crash report that the user can review and choose to send.

`CrashLog.kt` does write crashes to `cacheDir/crashes/` and shows a "share with support" notification — but this requires the user to actively forward the log. A real support path is: "tap a button → crash log + app version + device model → opens a pre-filled email to support."

**What's missing:** a "Report a problem" button somewhere in Settings → About that bundles the latest crash log + version info into a `mailto:` intent.

**Effort:** 1 day. **Risk:** none.

## B. Enterprise-readiness gaps (multi-officer, departmental IT, compliance)

### B1. No organisational deployment target — **FUNDAMENTAL**

**Observation:** The threat model and production-readiness plan both assume "IPS officer / SP-of-district" as the persona. There is no named organization — no specific Indian state police department, no specific IT cell, no specific security clearance process. The project is a single-officer local-only tool.

"Enterprise" means "this org will buy it, deploy it to 200 officers, and have a procurement process that requires X, Y, Z". None of that exists because **no org has committed to deploying Baton**.

**What's missing:** a deployment partner. Until then, the "enterprise" goal is aspirational, not actionable.

**Effort:** cannot be solved in code. **Risk:** scope-creep risk — building for an enterprise that never buys is wasted work.

**Honest take:** the most useful thing the user can do is **not** try to make Baton "enterprise-ready" before an enterprise commits. Better: keep it single-officer-grade, let the open-source community pick it up, and only respond to enterprise demand when it arrives.

### B2. No multi-tenant data isolation — **HIGH (if a tenant appears)**

**Evidence:**
- Supabase auth is wired (`AuthRepository.kt`) with email-OTP sign-in.
- `PersonRepository`, `InstructionRepository`, etc. all have Supabase methods that take no user/tenant filter (the docs say RLS is enforced at the DB level).
- I cannot find the RLS migration. The repo has `supabase/migrations/` mentioned in `AGENTS.md` module layout but the directory is not present in the current tree:

```
$ ls supabase/
(empty)

$ find . -path "*/supabase/migrations*" -not -path "*/.git/*"
(no output)
```

**What's missing:** the RLS policies themselves. The MCP server contract (PR #8) says "all tools scope to `auth.uid()`" but the migration that creates those policies is not in the repo.

**Effort:** 1 day to write the RLS migration + 1 day to test. **Risk:** **CRITICAL** if deployed without — a single anon key could read every officer's casework.

### B3. No multi-device-on-one-account sync — **HIGH (if multi-device is desired)**

**Evidence:** `app/src/main/java/com/baton/app/data/local/SyncEngine.kt` is a single-user outbox. There is no device-to-device sync, no sync conflict UI in the app, no "this change is from another device" indicator.

**What's missing:** the `SyncConflictScreens.kt` is mentioned in PR #1's diff (`ui/settings/SyncConflictScreens.kt`) but I cannot find it:

```
$ find app/src -name "SyncConflict*"
(no output)
```

So the conflict resolution UI is referenced but not implemented. A multi-device deployment would silently drop one device's edits.

**Effort:** 1 week. **Risk:** high for multi-device deployments.

### B4. No retention enforcement — **HIGH (if compliance matters)**

**Evidence:** `RetentionPolicy.kt` defines the policy (7y audit, 3y captures, 3y dates, 7y instructions). `RetentionWorker.kt` is mentioned in the module layout but:

```
$ find app/src -name "RetentionWorker*"
(no output)
```

So the worker that *enforces* the policy is not in the tree. Data accumulates forever. BNSS §152A compliance requires the 7-year retention to be enforced, not just declared.

**What's missing:** `RetentionWorker.kt` (already partially written in some branch but not on main) + a CI test that asserts "after 7 years, audit events are redacted".

**Effort:** 2 days. **Risk:** high for compliance.

### B5. No data export / portability — **MEDIUM**

**Evidence:** `app/src/main/java/com/baton/app/data/export/PlainExporter.kt` exists. CSV + JSON export. Good.

What's missing: a tested restore path. `BackupManager.kt` is referenced but not in the tree. So the user can export, but cannot reliably import.

```
$ find app/src -name "BackupManager*"
(no output)
```

**Effort:** 2 days. **Risk:** medium — restore is where backups actually earn their keep.

### B6. No SLAs, no monitoring, no on-call — **FUNDAMENTAL**

**Observation:** there is no monitoring agent, no error rate dashboard, no pinging, no uptime measurement. The `CrashLog.kt` writes to local file. If the app crashes for 100% of users, nobody knows.

**What's missing:** Sentry or a self-hosted alternative. The privacy posture rules out Crashlytics (it sends data to Google). A self-hosted Sentry is feasible.

**Effort:** 1 week. **Risk:** can't see your bugs in production.

### B7. No support tier / SLA — **FUNDAMENTAL**

There is no support tier. The support email is a ProtonMail address with no SLA. No helpdesk, no triage, no on-call. Enterprise customers require this.

**Effort:** cannot be done in code. **Risk:** blocks any enterprise sale.

### B8. No third-party security audit — **HIGH (before any production deployment with real data)**

The threat model is an internal design document. It has not been reviewed by a security professional. The "Verified" claim in `## See also` of the threat model is internal-only.

**What's missing:** a paid security review of the SQLCipher key derivation, the audit chain signing, the Supabase RLS, the FLAG_SECURE recovery screen, and the voice-capture privacy path.

**Effort:** $5k-$20k for a 1-week audit. **Risk:** high — without this, you don't know what you don't know.

## C. Things that look production-ready but aren't — **honest corrections**

The critical review's 7.0/10 included several "looks good" items that, on closer inspection, are less solid than they appear:

| Claimed in critical review | Real state | Verdict |
|---|---|---|
| "552 unit tests across 72 files" | True. But **zero** of them run on a real device. `app/src/androidTest/` is referenced in the module layout but the directory is effectively empty (only `M0AcceptanceTest.kt` mentioned, not present). | Tests are JVM-only. Real-device behaviour is unverified by automation. |
| "Self-hosted CI is green" | True for the most recent clean run. But the cache upload step has hit 30-min timeouts in earlier runs. The CI is **flaky** — green today, cancelled tomorrow. | CI is functional but not stable. |
| "Vault mode + PIN works" | True, manual test. But the PIN unlock path is **behavioural deniability only** (per threat model §3.2). A forensic attacker reads the SQLCipher DB and sees the vaultMode column. Not cryptographic. | Vault mode is honest about its limits but should not be sold as encryption. |
| "FLAG_SECURE blocks screenshots of the recovery phrase" | True, manual test (screenshot was black). But FLAG_SECURE is **advisory** on Android — a rooted device or accessibility-service attacker can bypass it. | Realistic threat model only. |
| "Privacy posture: no third-party AI" | Partially true. ML Kit OCR is on-device. Voice capture uses the **system** SpeechRecognizer, which is **not** guaranteed to be on-device. | The README's "no third-party AI" is a lie about voice capture. Document in threat model §3. |
| "v1.9.5 APK is 23 MB" | True for the arm64 split. The universal APK is 94 MB. The user-installed size on a real device depends on which split the Play Store delivers. | Mitigated by per-ABI splits (v1.9.1). |

## E. The honest, un-fudged version

What stands between Baton v1.9.8 and a real officer using it daily:

1. The 12-word recovery phrase has never been tested end-to-end on a wiped device. **The user's casework could be lost on the first phone-theft event.**
2. The "multi-device" claim in the README is unverified because no real Supabase is wired.
3. The RLS migration that protects multi-tenant data is not in the repo.
4. The retention worker that enforces BNSS §152A compliance is not in the tree.
5. AGENTS.md lies about llama.cpp / Whisper still being part of the stack.
6. The "no third-party AI" claim is a lie about voice capture.
7. The CI is green today but has hit cache-upload timeouts in the past.
8. There is no security audit, no code review process, no second pair of eyes on the threat model.

What does NOT stand between v1.9.8 and daily use:

- The code is readable, well-commented, and the design rules are applied.
- The 552 JVM tests are real and catching regressions.
- The privacy posture is thoughtful (on-device ML Kit, local-first crash log, FLAG_SECURE).
- The single-user threat model is internally consistent.
- The performance is fine for the 200-instruction fixture.
- The a11y is at least partially audited.
- The Play Store screenshots are honest about being placeholders.

So: this is a credible open-source project that has not yet earned the "production" label because **the operational and compliance work has not been done**, and has not earned the "enterprise" label because **no organisation has committed to deploying it**.

That's the honest answer. No "almost there" softening, no "ready to ship tomorrow" hype. The path is clear and the work is concrete. The next 2-4 weeks of focused work on A1-A7 + B2-B5 would put the project at "I would put this in front of a real officer for a 30-day pilot with a real support contact" — which is the goal.
