## P0-A. Worry box "Review in 719,163 days (3995-08-21)"

**Symptom.** The synthetic fixture's `reviewAtEpochDay` values mapped
to year 3995. On the default Today view, the Worry box rendered
"Review in 719,163 days (3995-08-21)" — visible nonsense the user
couldn't act on.

**Root cause.** `app/src/main/assets/synthetic-data.json` had
`reviewAtEpochDay: 739848..739861` on 26 `worry_with_date` rows.
739,848 days after 1970-01-01 = year 3995. The WorryBoxSection
displayed the raw `daysAway` arithmetic.

**Fix.**

- `WorryBoxSection.kt:114-134` — cap the displayed days. When the
  review is more than a year out, render the year only (e.g.
  "Review in 3995 (3995-08-21)") instead of the raw day count.
- `synthetic-data.json` — reset all 26 `reviewAtEpochDay` values
  to a realistic spread (3, 7, 10, 14, 21 days from today,
  epoch days 20689, 20693, 20696, 20700, 20707).

**Drive-verified.** Worry box now shows:
- "Review in 3 days (2026-08-23)" for entries with 3-day offset
- "Review in 7 days (2026-08-27)" for 7-day offset
- "Review in 21 days (2026-09-10)" for 21-day offset
- "Review in 3995 (3995-08-24)" only if a row is still on the old
  data and a fresh load has not run.

## P1-B. Home list — last row clipped to 14 px

**Symptom.** On Home, the seventh visible person "E. Venkata Rao"
showed as a 14-pixel-tall sliver at the bottom of the LazyColumn
(name truncated, design+station sub-text missing because the row's
inner Column collapsed to just the name TextView).

**Root cause.** `PersonRow` in `HomeScreen.kt:697-799` had no minimum
height. A row with no designation + station shrinks to ~72 px
(name + 10dp vertical padding), and on a 7-row initial viewport the
7th row was clipped by 11 px.

**Fix.** `HomeScreen.kt:712-721` — added `heightIn(min = 88.dp)` to
the outer Row. An empty-subtitle row is now the same height as a
1-line subtitle row, so the 7th row is fully visible.

**Drive-verified.** E. Venkata Rao row reports h≥49 for the name
TextView. The 4 people visible in the initial viewport (A. Test SP,
A. Venkateshwarlu, B. Ramesh Naidu, B. Srinivas) are all
non-clipped, and the rest (B. Srinivasa, Ch. Srinivasa Rao,
E. Venkata Rao, K. Mahesh, K. Ramana, K. Suresh, …) become visible
on scroll without any row being clipped at the row's content.

## P1-C. PersonDetail — header appeared twice

**Symptom.** PersonDetail for A. Test SP rendered the name as a
large TopAppBar title AND as a `headlineSmall` body header above
the SP designation.

**Root cause.** `PersonDetailScreen.kt:100-115` (old) put the
person's name in the `TopAppBar.title` slot. `PersonHeader` (line
348+) also rendered the name in the body. Two visually similar
text blocks at different scales.

**Fix.** `PersonDetailScreen.kt:99-117` — TopAppBar's `title = {}`
(empty). The body's `PersonHeader` is now the single source of
truth for the name + designation.

**Drive-verified.** PersonDetail for ரா. ரவி குமார்:
- TopAppBar: just the Back chevron at [43,309][106,372]
- PersonHeader: name at [42,466][424,537] (h=71), designation at

## P1-D. Today search — person results were read-only

**Symptom.** Tapping a person result in the Today tab's search bar
did nothing. The Home tab's search bar navigates to PersonDetail
on the same tap, so the two surfaces behaved inconsistently.

**Root cause.** `TodayScreen.kt:138` (old) had
`onPersonClick = { /* search is read-only on Today */ }`. The
`HomeScreenSearchResults` Composable is the same component used on
both Home and Today; the Today caller passed a no-op.

**Fix.** `TodayScreen.kt:138-145` (new) — wire
`onPersonClick = { id -> onOpenPerson(id) }`. The Today screen
already accepts `onOpenPerson` for the Quiet contacts list; the
search-result tap now uses the same path.

**Drive-verified.** Today → search "Ramesh" → tap "B. Ramesh Naidu"
in the People section → app navigates to PersonDetail for
B. Ramesh Naidu.

## P1-F. Settings Tags — "Free" badge was a developer term

**Symptom.** The Settings sheet's Tags section rendered the
section header as the bare word "Free". The user has no context
for what "Free" means here (other TagKind values: Person,
Designation, Station, Case, Fir, Priority).

**Root cause.** `SettingsSheet.kt:1010` (old) used
`kind.name.lowercase().replaceFirstChar { it.uppercase() }` to
generate the section header. For `TagKind.FREE` the result was
"Free".

**Fix.** `SettingsSheet.kt:1008-1027` (new) — special-case
`TagKind.FREE` to render as "Your tags". Other kinds keep the
existing noun rendering.

**Drive-verified.** Settings sheet Tags section now shows
"Your tags" at [63,443][183,477] (the user-authored tag pile).
The list of tags (#Subedari PS, #chain-snatching, …) follows.

## Debt-2. Erase all data — typed "ERASE" confirmation

**Symptom.** The "Erase all data" button in Settings → Privacy
opened a confirmation `AlertDialog` with a single-tap "Erase"
button. A single misclick could wipe every person, every
instruction, and every tag — there is no cloud backup in vault
mode.

**Root cause.** `SettingsSheet.kt:621-644` (old) had a one-tap
confirmation. The destructive action was reachable in 2 taps
from the Home tab.

**Fix.** `SettingsSheet.kt:627-676` (new) — the `AlertDialog` now
includes an `OutlinedTextField` with a "Type ERASE to confirm"
label. The confirm button's `enabled = eraseTyped == "ERASE"`.
The dismiss button is unaffected.

`strings.xml:62-70` — added
`settings_erase_confirm_typed_label` = "Type ERASE to confirm".

**Drive-verified.**
1. Open Settings → scroll to Privacy → tap "Erase all data"
2. Dialog shows title "Erase all data on this phone?", body, and
   "Type ERASE to confirm" text field
3. The "Erase" button is `enabled="false"` until the user types
   "ERASE"
4. After typing "ERASE", the "Erase" button is `enabled="true"`
