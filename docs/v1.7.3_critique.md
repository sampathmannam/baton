## 1. New P0 — worry box still shows "Review in 3995" for existing users

### P0-A. Stale seeded data on upgrade

**Symptom.** On Today → scroll past Quiet contacts → Worry box section
shows entries like:

```
"हिन्दी शीर्षक"
"41 CrPC report due for 3 cases. Need to be filed by 22 Au..."
"Review in 3995 (3995-08-21)"          ← still year 3995
[ Review and let go ]  [ Keep ]
```

The cap from v1.7.2 (P0-A) IS working — the day count is bounded to
year-only, so we see "Review in 3995" instead of "Review in 719,163
days". **But the underlying date is still year 3995.** A user who
upgraded from v1.7.1 → v1.7.2 sees the same nonsense date as before
v1.7.2.

**Root cause.** v1.7.2's fix to `synthetic-data.json` changed the
`reviewAtEpochDay` values from `739848..739861` (year 3995) to
`20689..20707` (days 3..21 from today). However:

- The fix only affects the **asset file shipped in the APK**. New
  installs get the new dates because the fixture loader reads from
  the new asset.
- **Existing users** already have a Room DB seeded with the old
  `739848..739861` values from v1.7.1. The new asset file is not
  re-imported on upgrade. The Room DB just keeps the old dates.
- The `SyntheticDataSeeder` only seeds if the DB is empty (or via the
  Settings → "Load test data" / "Clear & reload" buttons, which the
  user has to tap manually).

**Evidence.**

```bash
$ adb -s emulator-5554 shell uiautomator dump /sdcard/ui_v173_worry.xml
# (Today screen, scrolled to Worry box)
[ 126, 762- 516, 799] w=390 h=37  Review in 3995 (3995-08-21)
[ 126,1213- 516,1250] w=390 h=37  Review in 3995 (3995-08-22)
[ 126,1700- 516,1737] w=390 h=37  Review in 3995 (3995-08-22)
```

The fixture on disk is the new one (verified):

```bash
$ grep reviewAtEpochDay app/src/main/assets/synthetic-data.json | head
      "reviewAtEpochDay": 20689
      "reviewAtEpochDay": 20693
      "reviewAtEpochDay": 20696
```

So the file is correct; the DB just has the old data.

**Fix.** Three options, in order of preference:

1. **Bump the fixture version, re-seed on version mismatch.** Add a
   `fixtureVersion: 2` constant to `SyntheticDataSeeder`. On `seed()`,
   check if the DB has a stored fixture version; if it's older than
   the asset's, run the seed again (replacing the old dates). The
   user-facing "55 people, 200 instructions, 16 tags" stat doesn't
   change because the fixture is the same shape.
2. **On `seed()` always compare-and-update** `reviewAtEpochDay`
   values from the asset. If the asset's value differs from the DB,
   take the asset's. No version bump needed; the asset is the source
   of truth.
3. **Document** the "Clear & reload" flow as the migration path.
   Smallest change; pushes the work to the user.

**Recommendation.** Option 1 — explicit fixture version makes future
fixture changes auditable. Real production users will hit this
otherwise.

**Acceptance.** On a v1.7.2 install with stale v1.7.1 data, after
upgrading to v1.7.3, the Worry box on Today shows dates within the
next 30 days for the dated worries, with no "Review in 3995" rows.

## 2. New P1 — first-impression data hygiene

### P1-B. Test-data placeholders still in fixture

**Symptom.** On Today → scroll through Quiet contacts, the list
contains obvious test placeholders:

```
[ 126,1152- 699,1301] w=573 h=149  XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
[ 126,1465- 699,1561] w=573 h=96   Person-with-many-hyphens-and-some-special-chars
```

These are embarrassing on a real user's phone.

**Root cause.** v1.7.1's T4 fix removed the `XXX.../AAAA...` text
placeholders and renamed some entries, but the fixture still includes
the X-string and the long-hyphen entries for layout testing. The
intent was to keep them for **layout** testing (long-name + special
chars), but they ended up in the default Quiet contacts list which a
user sees on first launch.

**Evidence.** `ui_v173_today.xml`:

```
[ 126,1152- 699,1301] w=573 h=149  XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
[ 126,1465- 699,1561] w=573 h=96   Person-with-many-hyphens-and-some-special-chars
[ 126,1633- 316,1749] w=190 h=43  B. Srinivasa
[ 126,1749- 265,1786] w=139 h=37  Constable
[ 126,1791- 488,1812] w=362 h=21  haven't touched in 59 days   ← clipped
```

**Fix.** Two options:

1. **Rename or remove the placeholder rows** in
   `synthetic-data.json`. If the goal is layout testing, rename them
   to realistic long names (e.g. "Syed Shah Rukh Khan Bahadur" for
   the 573px name, "Ch. Vijaya Raghava Reddy Gajapathi Raju" for
   the long-hyphen entry).
2. **Move the placeholder data to a separate fixture** that's only
   used by the test data button, not the default seed.

**Recommendation.** Option 1 — keep the layout coverage but make
the names plausible. The 573px name covers the "name takes full
width" case; the long-hyphen entry covers the "hyphens in unusual
places" case. Both can be realistic.

**Acceptance.** No `X*` or `*-with-*-special-chars` placeholders
in the default Quiet contacts list. Long-name layout coverage
preserved.

### P1-C. "Export as CSV or JSON" has no radio/checkbox state

**Symptom.** Settings → Data → "Export as CSV or JSON" section shows
two text labels:

```
[ 136, 660- 457, 713] w=321 h=53  CSV (Excel-friendly)
[ 737, 660- 830, 713] w= 93 h=53  JSON
```

There is no visible radio / checkbox / "selected" indicator. The
user has no way to tell which format will be used.

**Root cause.** v1.7.0 critique St2 ("CSV/JSON no radio state") was
explicitly **out of scope** for v1.7.1, v1.7.2, and now v1.7.3. It's
been deferred through 3 milestones.

**Evidence.** `ui_v173_settings2.xml`:

```
[ 136, 660- 457, 713]  CSV (Excel-friendly)   clickable=true
[ 737, 660- 830, 713]  JSON                   clickable=true
```

The buttons are clickable but don't visually indicate which is
selected. The current default is CSV (per `ExportViewModel`); users
who want JSON have to know the default.

**Fix.** Add a small `RadioButton` to the left of each label, bound
to the same `selectedFormat` state. Two `Row`s, each with a
`RadioButton` + `Text`. The selected radio lights up.

**Acceptance.** Settings → Data → Export shows a visible radio dot
on the currently-selected format (CSV by default). Tapping JSON
moves the radio dot to JSON.

### P1-D. H3 — M3 NavigationBarItem `clickable=false` on the active tab (deferred from v1.7.0)

**Symptom.** All three bottom-nav tab children show
`clickable=false` in the UI hierarchy, including the text label and
icon:

```
[ 131,2001- 215,2043]  clickable=false  cls=TextView  text="Home"
[ 141,1917- 204,1980]  clickable=false  cls=View       (home icon)
[ 498,2001- 582,2043]  clickable=false  cls=TextView  text="Today"
[ 508,1917- 571,1980]  clickable=false  cls=View       (today icon)
[ 849,2001- 964,2043]  clickable=false  cls=TextView  text="Settings"
[ 875,1917- 938,1980]  clickable=false  cls=View       (settings icon)
```

The actual click handler on the parent `Surface` does fire
(verified on ZD2232FCR5 in v1.7.0). But the active tab cannot be
re-tapped to scroll-to-top (or any other "I'm on this tab, re-tap
to refresh" affordance).

**Root cause.** M3 `NavigationBarItem` doesn't expose clickable on
its children when the item is `selected=true`. This is by design in
Material 3 but conflicts with the iOS-style "tap active tab to
scroll to top" pattern.

**Fix.** Replace the M3 `NavigationBarItem` in `MainActivity.kt` (or
wherever the bottom nav lives) with a custom `Row` that:
1. Always reports `clickable=true` on the active tab.
2. Calls `onReselected` when the active tab is tapped again
   (`currentDestination == item.destination`).

For the "scroll to top" hook: each tab's root composable can expose
a `BringToTop` callback via `CompositionLocal` or a `NavBackStackEntry.savedStateHandle`. On re-tap, the activity-level nav handler invokes
the saved-state hook.

**Recommendation.** This is a bigger change than the others but
it's been deferred for 3 milestones. v1.7.3 is the right place to
land it. ~80 lines of code; risks are visual parity with M3
(styling might shift slightly) and the BringToTop plumbing (needs
to be threaded through `NavController` + each tab's root).

**Acceptance.** uiautomator dump on Home shows `clickable=true` for
the Home tab's text and icon. Tapping Home while already on Home
scrolls the Home list to the top.

## 3. New P2 — clipped rows and layout polish

### P2-A. B. Srinivasa h=21 clipped row in quiet contacts

**Symptom.** Scrolling to the bottom of Quiet contacts on Today,
the last row shows:

```
[ 126,1706- 316,1749] w=190 h=43  B. Srinivasa
[ 126,1749- 265,1786] w=139 h=37  Constable
[ 126,1791- 488,1812] w=362 h=21  haven't touched in 59 days   ← h=21 vs h=37 for others
```

The "haven't touched in N days" subtitle is half-clipped (h=21
instead of h=37).

**Root cause.** Same family as v1.7.2 P1-B: the inner Column
collapses when the natural height of the list hits the parent's
contentPadding + visible area boundary. v1.7.2's fix added
`heightIn(min = 88.dp)` to the `PersonRow` on Home, but the
**quiet-contacts row** in `TodayScreen` (a separate composable
with the same shape) wasn't updated.

**Fix.** Apply the same `heightIn(min = 88.dp)` to the quiet-contacts
person row in `TodayScreen.kt`. Alternatively, factor both row
shapes into a shared `PersonListRow` composable so the constraint
lives in one place.

**Recommendation.** The second (shared composable) is cleaner but
bigger; the first is the targeted fix. Ship the first; refactor
later.

### P2-B. Worry box subtitle h=7

**Symptom.** Scrolled to the Worry box header:

```
[  84, 485- 275, 491] w=191 h=  6  Worry box
[  84, 512- 583, 549] w=499 h=37  Things you wanted to come back to.
```

The "Worry box" title is at h=6 (vs h=43 for the subtitle). Likely
a layout glitch where the section header TextView is positioned
just before the section content but the dump shows partial bounds.

**Root cause.** Probably the section is at the top of the visible
viewport after a scroll, and uiautomator captures only the visible
portion. The y=485 is a clipped top of the section title. Not a
real bug; a fully-scrolled view would show the full h=43 title.

**Action.** Re-verify after the P0-A fix lands. If the h=6 is still
showing in a clean state, file as a real layout bug; otherwise
mark as a dump-capture artifact.

### P2-C. "(unknown person)" row in Today search results clipped

**Symptom.** Today → search "Ramesh" → bottom of results:

```
[ 105,1807- 335,1812] w=230 h=  5  (unknown person)
```

A row at h=5, clearly clipped.

**Root cause.** Same shape as P2-A — the search result list doesn't
constrain its bottom row's height when scrolled to the edge of the
visible area.

**Fix.** Add `contentPadding(bottom = 16.dp)` to the search result
`LazyColumn` and/or `heightIn(min = 88.dp)` on the
`SearchResultRow`.

**Action.** Bundle with the P2-A fix if a shared `PersonListRow`
composable is factored.
