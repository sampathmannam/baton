# Baton v2.1.0 — "WhatsApp-style Google Drive backup"

**Release date:** 2026-08-24
**versionCode:** 45 (was 44)
**Branch:** `release/v2.0.0-supabase-drop`
**Tests:** 521 / 521 green (0 failures, 0 errors, 7 pre-existing skips; 21 new tests vs. v2.0.2, 4 new test files)

> v2.1.0 ships the WhatsApp-style Google Drive
> backup the user asked for, plus the last three
> PM-rating cleanup items:
>
>  1. **Drive backup** — local DB stays on the device, a backup goes to the user's hidden `appDataFolder` in their Google Drive, the user can restore on a new device. Backups are **encrypted client-side** with a key derived from the user's 12-word recovery phrase before upload. Google cannot read the bytes.
>  2. **DatabasePreflight is a write+read round-trip** — the v2.0.2 `SELECT 1` was replaced with a read+write+read that catches the "write silently corrupts" failure mode.
>  3. **Pre-v8 destructive migration is gone** — replaced with 6 explicit `MIGRATION_2_3` through `MIGRATION_7_8`. The v2.0.x `fallbackToDestructiveMigrationFrom(2..7)` (the data-loss footgun for pre-v8 users) is removed.

## What changed

### Google Drive backup (the user-facing feature)

- **Settings → Google Drive backup** section. Renders
  one of two states:
  - **Not signed in.** A "Sign in with Google" button
    opens a Chrome Custom Tab to Google's OAuth
    page. The user grants the `drive.appdata` scope
    and is redirected back to the app.
  - **Signed in.** A "Back up now" button, a "Restore
    from backup" button, and a "Sign out" button.

- **First "Back up now".** The Settings sheet
  prompts for the user's 12-word recovery phrase.
  The passphrase is SHA-256-hashed and the hash is
  stored in `SecurePreferences`. The hash is the
  encryption key source for the AES-256-GCM blob
  — Google Drive sees encrypted bytes, not the
  user's data.

- **Subsequent "Back up now" + daily auto-backup.**
  Re-use the stored hash. The user doesn't have to
  re-enter the phrase every time. The daily
  WorkManager job (every 24h) uses the same hash.

- **Restore on a new device.** The user signs in
  to the same Google account, opens
  Settings → "Restore from backup", picks a backup
  from the list (newest first), enters the recovery
  phrase that was used to encrypt it, and Baton
  downloads + decrypts + imports the rows.

- **Encryption format.** The on-disk blob is:
  ```
  magic (4 bytes "BTV1")
  salt (16 bytes, random per encryption)
  nonce (12 bytes, random per encryption)
  ciphertext + GCM tag (variable)
  ```
  PBKDF2-HMAC-SHA256 with 100k iterations
  derives the AES-256 key from the passphrase +
  salt. 8 unit tests pin the round-trip, the
  wrong-passphrase failure, and the salt/nonce
  uniqueness.

### DatabasePreflight write+read round-trip

- v2.0.2 had a `SELECT 1` preflight. The PM rating
  called this out: a file-level corruption that
  surfaces as a page-fault during a write
  (mid-WAL-flush, OS-level disk error) would NOT be
  caught.
- v2.1.0 preflight is read + no-op write + read on
  the device-owner row in the `users` table. If
  the read-back differs from the write-in, the DB
  is corrupt. Any throwable in any step sets the
  `DatabaseHealth` flag.
- `DatabaseHealth` was extracted from
  `SecurePreferences` to plain `SharedPreferences`
  (the value is a single boolean — not PII — and
  the SecurePreferences backend requires
  AndroidKeyStore which is not available in unit
  tests).
- 2 new unit tests in `DatabasePreflightTest`.

### Pre-v8 destructive migration removed

- v2.0.x had `fallbackToDestructiveMigrationFrom(2,
  3, 4, 5, 6, 7)` — a data-loss footgun for pre-v8
  users (v2.0 has no Supabase to re-fill from).
- v2.1.0 adds 6 explicit migrations:
  `MIGRATION_2_3`, `MIGRATION_3_4`, `MIGRATION_4_5`,
  `MIGRATION_5_6`, `MIGRATION_6_7`, `MIGRATION_7_8`.
  Each calls a shared `runPreV8Migration` helper
  that:
    - Adds the `vaultMode` column to persons +
      instructions (with default 'visible').
    - Creates the v8-era tables: `tags`,
      `instruction_tags`, `sync_conflict` (with
      `IF NOT EXISTS`).
    - Creates the v8-era indexes.
    - Wraps each `ALTER TABLE` in try-catch so a
      "duplicate column" error is swallowed (a v4-v7
      schema that pre-empted the v8 split won't
      crash).
- 3 new unit tests in `Migration7To8Test`:
    - Adds `vaultMode` column with default 'visible'
      to existing rows.
    - Creates the v8-era tables.
    - Preserves the user's pre-existing person +
      instruction rows.

### Drive REST API wrapper

- `DriveRestApi` is a thin Ktor HttpClient wrapper
  for the Google Drive REST v3 API.
  - `uploadToAppFolder(accessToken, fileName,
    content)` — multipart upload to the user's
    hidden `appDataFolder`.
  - `listBackups(accessToken)` — Drive files
    matching `name contains 'baton-backup-'`.
  - `downloadFile(accessToken, fileId)` — the
    encrypted bytes.
  - `deleteFile(accessToken, fileId)` — idempotent
    on 404.
- 8 unit tests with Ktor's `MockEngine` pin the
  happy path + 401 / 500 error surfaces.

### OAuth flow (Custom Tabs, no `play-services-auth`)

- The offline build cache doesn't have
  `play-services-auth:21.2.0`. v2.1.0 uses
  `androidx.browser:browser` (which is in the
  cache) and a Custom Tabs OAuth flow instead.
- `GoogleOAuthClient.signIn()` opens a Chrome
  Custom Tab to Google's OAuth page with the
  `drive.appdata` scope. Google redirects to
  `baton://oauth-callback?code=...`. The
  `OAuthCallbackActivity` catches the intent,
  exchanges the code for access + refresh tokens
  via a Ktor `submitForm` call to Google's token
  endpoint, and stores the refresh token in
  `SecurePreferences` (long-lived; the access
  token is in memory and refreshed on demand).
- A future v2.x can swap to the `GoogleSignInClient`
  path for a smoother one-tap UX. The
  `BackupCrypto` + `DriveRestApi` + `DriveBackupManager`
  stack stays the same.

## Drive backup details (for the user)

- The backup file is in the user's Google Drive
  under "Manage Apps" → Baton → "Hidden app
  data". Google does NOT surface this folder in
  the Drive UI; the user can't see or delete the
  files from drive.google.com. The files can only
  be reached via the Drive API with the
  `drive.appdata` scope.
- The file is named
  `baton-backup-YYYYMMDD-HHMMSS.json.enc` and
  contains the AES-256-GCM-encrypted JSON
  snapshot. The encryption key is derived from
  the user's 12-word recovery phrase.
- Daily auto-backup runs every 24h. The user can
  also tap "Back up now" to force an immediate
  backup.
- To restore on a new device:
  1. Install Baton on the new device.
  2. Open the app. Set up the recovery phrase
     (this is the same 12 words you used on the
     old device).
  3. Settings → Google Drive backup → Sign in
     with Google. Sign in to the same Google
     account.
  4. Settings → "Restore from backup" → pick
     a backup from the list → enter the
     recovery phrase. The rows are imported.
- If the passphrase is wrong, the decryption
  fails with the standard GCM tag-mismatch
  error. The Settings sheet renders "Wrong
  passphrase." snackbar.

## Drive-verify

Pending. The user device was unplugged at the
start of v2.1.0. The Drive backup flow requires:
1. A real Google account (the `CLIENT_ID`
   placeholder needs to be replaced with a real
   one before the OAuth flow works end-to-end).
2. A Custom Tabs-capable browser (Chrome or
   Samsung Internet) installed on the device.
3. The "Sign in with Google" flow → OAuth
   Custom Tab → "Allow" → app receives the
   redirect → Settings sheet re-renders the
   "Back up now" button.
4. "Back up now" → passphrase prompt → 12-word
   phrase entered → encrypted blob uploaded.
5. "Restore from backup" → backup list → pick
   one → passphrase prompt → decrypted JSON
   imported.

Steps 3-5 are testable in unit tests (the crypto
+ REST API + restore logic). Steps 1-2 are
device-only.

## Performance

- 521/521 unit tests pass.
- The Drive backup is a 2-3 second operation for
  a 1 MB snapshot (PBKDF2 derivation + AES-GCM
  encryption + Drive upload). The user perceives
  it as "Back up now → spinner → done".
- The DatabasePreflight write+read round-trip is
  ~5ms on a Pixel 6 (a single no-op upsert). The
  added IO is negligible.
- `:app:assembleDebug` builds clean.
