## What changed

### 1. Atomic `create()` in `RoomInstructionRepository` (P0 production blocker)

`RoomInstructionRepository.create` was writing to four tables
in four sequential coroutine steps:

1. `InstructionDao.upsert(entity)` — the main row
2. `InstructionFtsDao.upsert(...)` — the FTS index entry
3. `SyncQueueDao.enqueue(...)` — the outbox row
4. `TouchPersonOnActivity.touch(personId)` — the auto-snooze bump

A process death or cancellation between (1) and (2) left the
FTS index pointing at a non-existent rowid (search broken
until the next reseed). A crash between (3) and (4) left the
decay view showing the user as "haven't touched in 30+ days"
for a person they had just saved an instruction about.

**Fix.** All four writes are now inside a single
`db.withTransaction { ... }` block. A throw inside the block
rolls back all four writes — Room's transaction machinery
buffers the writes and rolls back on exception. Either all
four land, or none do.

**Verification.**
`RoomInstructionRepositoryCrashRecoveryTest` (Robolectric +
real `Room.inMemoryDatabaseBuilder`):

- `create rolls back all four writes when PersonDao touch throws` —
  drives a `RuntimeException` from inside the `touch` call,
  asserts the exception surfaced, asserts the instruction
  table is empty, asserts the sync queue has no
  PENDING_INSERT entry, asserts `PersonDao.touch` was
  invoked exactly once.
- `create lands all four writes when no side effect throws` —
  asserts the instruction row, the FTS row (implied), the
  sync queue entry, and the `PersonDao.touch` call all
  landed with the expected IDs.

Why Robolectric + real Room, not mocks: the whole point of
the fix is the cross-table atomicity that Room's transaction
implementation provides. Mocking `AppDatabase` would prove
nothing — `withTransaction { }` on a mock is a no-op. The
real SQLite transaction machinery is exercised, including the
implicit rollback on exception.

### 2. AppInitializer auto-reseed is now debug-gated (A6 audit fix)

The v1.9.8 audit flagged this as a "data-persistence
quirk" (the description was imprecise — the wipe doesn't
happen on *every* launch, just on the first launch of a
release build that has never loaded the fixture). The real
bug:

- The `synthetic-data.json` asset carries `version: 2`.
- The asset ships in every build, debug and release.
- `AppInitializer.runOnAppStart` calls
  `FixtureLoader.reseedIfStale()` on every launch (NOT
  debug-gated, per the v1.7.3 rationale).
- `reseedIfStale` checks `storedVersion < asset.version`. On
  a fresh install, `storedVersion = 0` and `asset.version = 2`,
  so the reseed runs.
- `reseedIfStale` calls `loadFromAssets` which clears all 6
  tables (persons / instructions / instructions_fts /
  captures / tags / instruction_tags) before re-inserting
  the synthetic fixture.

Net effect: a release-build user who never touched the
debug menu had their data wiped on the very first launch,
and the synthetic fixture (designed to find UI bugs on a
12-row sample) replaced it. Subsequent launches were a
no-op (the wipe had already happened and `storedVersion` was
set to 2) — but the damage was done on launch #1.

The v1.7.3 comment claimed this was fine for "private R&D
with a single user, the trade-off is right". The v1.7.3→v1.7.2
scenario that justified the original behaviour (the "worry
box year 3995" dates) was for **synthetic-fixture data**,
never real user data, and a release-build user would not
benefit from the auto-update because they never loaded the
fixture in the first place. The "trade-off" was wrong.

**Fix.** The `reseedIfStale` call in `AppInitializer` is now
wrapped in `if (isDebugBuild) { ... }`. The `isDebugBuild`
property defaults to `BuildConfig.DEBUG` (true in `debug`,
false in `release`) and is `@VisibleForTesting` so a unit
test can verify the release-build contract without
recompiling against the `release` variant.

**Verification.** `AppInitializerTest` gains two new tests:

- `A6 release build does not call reseedIfStale on app start` —
  flips `isDebugBuild = false`, calls `runOnAppStart`, asserts
  the `FixtureLoader.reseedIfStale` mock was invoked exactly
  0 times.
- `A6 debug build still calls reseedIfStale on app start` —
  locks the existing dev-workflow behaviour; the assertion
  is a no-op (`assertTrue(true)`) because Robolectric's
  classpath doesn't include `libsqlcipher.so` (the
  `loadLibrary` call throws and the v1.2.1 BUG-DATA-021 fix
  returns early before the reseed is launched). A real
  device / emulator verification is on the drive-verify
  list; see "For users updating from v1.9.8" below.

The release-build path is now safe: a user who installs
v1.9.9 on a phone with existing v1.9.8 casework will not
have their data wiped on the next launch.

### 3. One-tap "Report a problem" in Settings → About (A10 audit fix)

The v1.9.8 audit said this was missing: "a 'Report a
problem' button somewhere in Settings → About that bundles
the latest crash log + version info into a `mailto:`
intent."

The audit was partly wrong: a "Share crash log" row already
exists (since v1.9.0) for the file-attachment + system
share-sheet flow. But the audit's specific request — a
`mailto:` with the crash log embedded in the body — was
genuinely missing, and the UX is materially better for
bug reports (one tap deep vs. tap + chooser).

**Fix.** New `Report a problem` row in Settings → About
(after the existing `Support` row, before the conditional
`Share crash log` row). Tapping it builds a `mailto:` intent
via the new `com.baton.app.ui.util.ReportProblemIntent`
helper:

- Subject: `Baton {version} problem report`
- Body: the user-visible "What happened?" prompt, plus
  version + device + Android version, plus a `--- Crash log
  (most recent) ---` section if a crash log exists in
  `cacheDir/crashes/` (via `CrashLog.mostRecent`).
- Falls back to the no-crash-log body if no crash log is
  present (proactive bug report).
- Distinct from the existing `Support` row (general
  question, no crash log embedding) and the conditional
  `Share crash log` row (file attachment via system share
  sheet).

**Why templates are parameters, not resource lookups.**
The project's Robolectric tests run without
`testOptions.unitTests.includeAndroidResources = true`
because that flag breaks 270+ other tests (see
`RecoveryPhraseHoldToRevealTest`'s class docstring for the
decision rationale). So `ReportProblemIntent.build` takes
the localised subject + body templates as plain `String`
parameters; the Settings sheet does the resource lookup in
its composable scope and passes the resolved strings. The
pure-function shape is trivially testable on the JVM.

**Verification.** `ReportProblemIntentTest` (Robolectric):

- `build without crash log uses no-crash body template` —
  asserts subject contains version name + "problem report",
  body contains version name + build code + device +
  Android release, body does NOT contain a "--- Crash log"
  section, mailto target is the support email.
- `build with crash log embeds the log text in the body` —
  writes a fake crash log to `cacheDir/crashes/`, asserts
  body contains the section header AND the crash log's
  `app_version` line AND the simulated exception class +
  frame.
- `build with empty crash log file and no-crash template
  does not produce a Crash log section` — locks the edge
  case where the caller passes the no-crash template (the
  Settings sheet's branch for `mostRecent == null`).

## For users updating from v1.9.8

- **No data migration.** Database v15 unchanged.
- **The Settings sheet has a new "Report a problem" row**
  (always visible, after the "Support" row). Tapping it
  opens the email composer with the version + device info
  pre-filled; if a crash log exists from a previous
  session, the log is embedded in the body so the support
  reply has the stack trace inline.
- **No change in on-device behaviour for the data-persistence
  fix in normal use.** A debug-build user (the typical R&D
  workflow) still gets the auto-reseed on app start; a
  release-build user no longer has the (formerly latent)
  data-wipe risk on first launch.
- **No change in the FTS search, sync queue, decay view, or
  any other surface.** The atomicity fix is a pure
  correctness improvement; the four writes still happen in
  the same order, just inside a transaction.
