**Date:** 2026-08-20
**Source:** v1.7.1 = commit `cce9d0a`, tag `v1.7.1` on `m0/skeleton-v1.7.0`
**Build:** 94 MB APK, `versionCode=27`, `versionName=1.7.1`
**Drive-verify target:** `emulator-5554` (Android 14, 1080x2400, 420dpi). Real phone
`ZD2232FCR5` offline (Tailscale: last seen 23h ago). Emulator is the valid

**Method:** Full fresh-eyes walkthrough + UI hierarchy dump on every screen +
static code review of the data layer, capture/search/today/home flows, and
the worry/decay/mood sub-views. The same `uiautomator dump` evidence used
to grade v1.7.0 (4.5/10) and that v1.7.1 closed is the source of truth here.

**Score:** 6.5/10 composite. v1.7.1 closed the v1.7.0 P0s (nav, count label,
NoteBar, Settings close) and the T1/T4/T5/P1 data hygiene items, but a fresh
walkthrough surfaces new P0/P1 issues that affect the worry box labels

## 1. New P0 — visible nonsense on the first Today scroll

### P0-A. Worry box "Review in 719,163 days (3995-08-21)"

**Symptom.** Open the Today tab → scroll past the brief and Quiet contacts →
the Worry box section shows entries like:

```
"हिन्दी शीर्षक"
"41 CrPC report due for 3 cases. Need to be filed by 22 Au..."
"Review in 719163 days (3995-08-21)"       ← P0
[ Review and let go ]  [ Keep ]
```

The number is absurd and the date is the year 3995. The user sees this on
the default Today view; no user action can hide it.

**Root cause.** `app/src/main/assets/synthetic-data.json` has
`reviewAtEpochDay: 739848..739860` on the `worry_with_date` instructions.
739,848 days after 1970-01-01 ≈ year 3995. The fixture was likely written
with these as a "far future review" test case, but the WorryBoxSection's
"Review in N days" label is straight arithmetic, so it surfaces the raw
extreme to the user.

**Evidence.**

```bash
$ grep reviewAtEpochDay app/src/main/assets/synthetic-data.json | head
      "reviewAtEpochDay": 739851,   # → 3995-08-22
      "reviewAtEpochDay": 739854,   # → 3995-08-25
      "reviewAtEpochDay": 739849,   # → 3995-08-20
      "reviewAtEpochDay": 739853,   # → 3995-08-24
```

**WorryBoxSection.kt:113-127** — `daysAway = today.toEpochDay() - day`
then `else -> "Review in ${-daysAway} days (${reviewDate})"`. No cap.

**Fix.** Two-part:

1. **Cap the displayed days** in
   `app/src/src/main/java/com/baton/app/ui/today/worry/WorryBoxSection.kt:121`:
   when `daysAway > 365`, render as a year count (`"in ~1968 years"`) or
   just the year (`"in 3995"`). The exact date is a fixture artifact and
   doesn't help a real user; the year round-up is the human-readable
   shape.
2. **Tighten the fixture** in
   `app/src/main/assets/synthetic-data.json`: change the `worry_with_date`
   rows to use epoch days within the next 30 days (e.g.
   `LocalDate.now().plusDays(7).toEpochDay()` style values), so the
   default Today view shows realistic "Review in 7 days" labels. The
   far-future case can stay as a single entry with `urgency: "worry"`
   (no review date) so the worry is still in the box but doesn't carry
   the absurd label.

**Acceptance.** After the fix, the Worry box on the default Today view
shows dates within the next 30 days for the dated worries, and any
far-future review label is at most `"in ~2 years"`.

## 2. New P1 — first-impression layout / data hygiene

### P1-B. Home list — last row clipped to 14 px

**Symptom.** On Home, the last visible person "E. Venkata Rao" shows as a
14-pixel-tall sliver at the bottom of the LazyColumn. The name is
truncated visually; the row's parent is clipped by the inner Scaffold's
contentPadding + visible area. User can scroll to reveal the full row,
but the initial state is broken.

**Evidence.** `ui_v172_home.xml`:

```
[42,1582][1038,1654]   w=996 h=72   E. Venkata Rao row     ← row clipped
[42,1608][326,1622]    w=284 h=14   E. Venkata Rao name    ← name h=14 (truncated)
```

Compare to other rows (e.g. A. Test SP at h=197, A. Venkateshwarlu at
h=197). The parent scrollable area is `[0,485][1080,1622]` — 1137 px.
Seven rows totalling ~1148 px, so the seventh row is 11 px short of the
visible area, and its internal name TextView gets the 14 px clip.

**Root cause.** `HomeScreen.kt:458-463` — the `LazyColumn`'s
`contentPadding(bottom = 88.dp)` is for the FAB clearance, but the sum
of seven person rows overflows the parent area by 11 px because the
synthetic fixture has 7 visible people in the first viewport. Adding
`lastInteractionAt` to the sort pushed "E. Venkata Rao" into the
seventh slot, where its empty `designation + station` sub-row means
the inner Column doesn't have the second TextView — the row's natural
height drops, but the parent's reserved contentPadding still gives the
seventh row a partial slot.

**Fix.** Two options:

1. **Cap the height of the `E. Venkata Rao` row** (or any row with no
   designation/station) so the missing second line doesn't shrink the
   row. The simplest: enforce a `minHeight = 88.dp` on the `PersonRow`
   in `HomeScreen.kt:698-799`.
2. **Add 16 dp bottom contentPadding** to the LazyColumn. The current
   `bottom = 88.dp` is correct for FAB clearance, but the row sum
   should also clear the visible area cleanly. Bump to `104.dp` so
   the seventh row is fully visible.

**Recommendation.** Option 1 (`minHeight` on the row) — it survives
future fixture changes and is the actual bug (a row with no sub-text
should still be readable).

**Acceptance.** E. Venkata Rao row reports h≥49 (name height) in
`uiautomator dump` on the initial Home view; no clip.

### P1-C. PersonDetail — header appears twice

**Symptom.** On PersonDetail for A. Test SP, the name is rendered as a
large "TopAppBar" header at the top, then again as a smaller "person
header" inside the body content, with the SP designation below. Two
visually similar text blocks at different scales.

**Evidence.** `ui_v172_persondetail.xml`:

```
[148,303][388,377]   w=240 h=74   A. Test SP           ← TopAppBar title
[42,466][282,528]    w=240 h=62   A. Test SP           ← PersonHeader (in body)
[42,528][1038,624]   w=996 h=96   Superintendent of Police (SP) • District...
```

**Root cause.** The PersonDetailScreen draws a `TopAppBar` with the
person's name (the `BackHandler`/title slot), then renders a
`PersonHeader` Composable inside the body content. Both show the name.

**Fix.** Pick one. The cleanest: **remove the name from the `TopAppBar`**
(just the back icon there) and let the `PersonHeader` carry the name
and designation. The TopAppBar becomes a quiet chrome element instead
of duplicating the body's primary content.

`app/src/main/java/com/baton/app/ui/home/PersonDetailScreen.kt:88-127`
— the `TopAppBar.title` slot renders `loaded.person.name`. Replace
with an empty title (or a chevron-only `IconButton` in the navigation
slot). The body's `PersonHeader` (around line 200+) is the primary
display surface.

**Acceptance.** `uiautomator dump` of PersonDetail shows the name
exactly once at a non-trivial height (≥49 px), with the SP designation
underneath.

### P1-D. Today search — person results are read-only

**Symptom.** On the Today tab, the search bar's results have two
sections: People and Instructions. Tapping a person in the People
section does nothing. Tapping an instruction opens the detail sheet.
Inconsistent with Home, where tapping a person navigates to the
PersonDetail screen.

**Evidence.** `TodayScreen.kt:138`:

```kotlin
onPersonClick = { /* search is read-only on Today */ },
```

**Root cause.** The `HomeScreenSearchResults` Composable is reused on
Today for visual parity, but the TodayScreen passes a no-op
`onPersonClick`. There's no wiring to route the tap to the
`onOpenPerson` callback the screen already accepts.

**Fix.** `TodayScreen.kt:138` — replace the no-op with the same
`onOpenPerson` callback the brief's "Quiet contacts" list already uses.
Both should route to the same person-detail destination.

```kotlin
onPersonClick = { id -> onOpenPerson(id) },
```

**Acceptance.** On Today, searching for a person, tapping the person
result, and the app navigates to the PersonDetail screen for that
person. The instruction tap path continues to open the
InstructionDetailSheet (no regression).

### P1-F. "Free" label in Settings / Capture tag section is opaque

**Symptom.** The Settings sheet's Tags section has a "Free" badge
above the list of free-form tags. The Capture sheet's tag picker has
the same "Free" badge. Users see "Free" with no context — is this
"free as in beer" or "free as in freedom"?

**Evidence.** `ui_v172_settings.xml`:

```
[63,443][118,477]   Free             ← badge
[105,482][970,525]  #Subedari PS     ← tag
```

**Root cause.** `TagKind.FREE` is the internal data-model kind
(free-form vs system vs smart). The UI labels it just "Free" with no
description. The "Free" label is a developer term that leaked into
the user-facing UI.

**Fix.** Replace `R.string.tag_picker_free_placeholder` (or whatever
the "Free" label resource is) with a more explicit label. Two
options:

1. Rename the badge to **"# Your tags"** or **"Your tags"** (the
   `#` prefix signals the user-created tag kind).
2. Drop the badge entirely. The tags speak for themselves.

**Recommendation.** Option 1 — keep a small label so the user
understands which kind of tag they're looking at, but make the
label self-explanatory.

**Acceptance.** `uiautomator dump` of Settings shows a section label
that reads as user-facing (e.g. "Your tags" or "# Your tags"), not
the developer term "Free".

## 3. Carry-overs from v1.7.0 (still open)

### Debt-1. Hardcoded colors in non-user-facing files

The v1.7.0 critique noted "~80 hardcoded colors in non-user-facing
files". Re-counting in v1.7.1: `grep -rn 'Color(0x' app/src/main/java/`
returns 33 hits, of which 30 are inside `ui/theme/Color.kt` /
`ui/theme/Theme.kt` (the theme package — correct) and 3 are
elsewhere:

- `features/tags/TagPicker.kt:190` — `Color(0xFF6F6F6F)` is the
  fallback when hex parsing fails. The literal duplicates
  `BatonColors.KindNeutralLight` (also `0xFF6F6F6F`). Replace with
  the token.
- `ui/components/BatonAccent.kt:125-126` — `Color(0xFF1F6F6A)` /
  `Color(0xFF4FB3AC)` are the brand accent pair (light/dark). These
  are deliberately standalone constants (not theme tokens) because
  they're used outside Compose context (e.g. the notification icon).
  Leave as-is.

**Action for v1.7.2.** Promote the one `TagPicker.kt` literal to the
token. The BatonAccent pair stays.

**Acceptance.** `grep -rn 'Color(0x' app/src/main/java/ | grep -v
'ui/theme/'` returns the two `BatonAccent` lines only.

### Debt-2. Onboarding validation

The v1.5.3 onboarding flow was simplified; v1.7.0's "what's NOT
verified" list still calls out onboarding validation as open. The
fixture loader and developer "Erase all data" / "Clear & reload" /
"Load test data" buttons are the only way to reset to a known state,
and there's no confirmation dialog for "Erase all data" beyond the
red text.

**Action for v1.7.2.** Add a confirmation `AlertDialog` to the "Erase
all data" button in `SettingsSheet.kt:2017-2043`. The dialog should
require a typed confirmation (e.g. "Type ERASE to confirm") — the
existing red text is not a sufficient gate for a destructive action.

**Acceptance.** Tapping "Erase all data" opens a confirmation dialog
that requires the user to type "ERASE" (or similar) before the action
fires. Cancelling dismisses without action.

### Debt-3. Layout / spacing fine-tuning

The v1.7.0 critique noted visual density and spacing fine-tuning as
deferred polish. The most visible artifact is the empty-state
"Add person" button padding (the v1.4 fix bumped it to be prominent
but the padding around the empty state is uneven — 32dp on the
Box + 20dp Spacer + 8dp arrangement + 80dp Spacer adds up
asymmetrically on the empty state).

**Action for v1.7.2.** Defer to a follow-up polish release; this is
P2-only and doesn't affect a user's ability to use the app.

### Debt-4. Settings sheet has no scroll-to-top affordance

**Action for v1.7.2.** Defer; the sheet is short enough that users
can scroll manually.
